# Security

## Reporting a vulnerability

Please **do not open a public issue** for security problems.

Use GitHub's private reporting instead: **Security → Report a vulnerability** on this repository. Include what you found, how to reproduce it and which version or image tag you tested. You will get an answer within a week; fixes are released as a new `latest` image and noted in the [changelog](CHANGELOG.md).

## Supported versions

Only the newest release (`astaldoo/tidewiki:latest`) receives security fixes. Database migrations run automatically on start, so updating is `docker compose -f docker.yaml pull && docker compose -f docker.yaml up -d`.

## Design

### Accounts

| Area            | Implementation                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Passwords       | Argon2id, 64 MiB, t = 3, p = 1, applied to an HMAC-SHA256 of the password keyed with a pepper derived from the master key. Old parameters are rehashed on the next sign-in. Concurrency is capped and the queue is bounded (HTTP 503 instead of memory exhaustion).                                                                                                                                        |
| Password policy | Minimum length 10–64 plus optional minimum counts of digits, special characters, upper- and lower-case letters; common passwords and the username/e-mail are rejected. Enforced on the server for registration, reset, change, admin-set and setup.                                                                                                                                                        |
| Unknown users   | A dummy hash is verified so timing doesn't reveal which accounts exist; error messages are identical.                                                                                                                                                                                                                                                                                                      |
| Lock-out        | Per account, escalating 10 min → 24 h. Counters for non-existent names are capped. A CLI unlock exists for the owner.                                                                                                                                                                                                                                                                                      |
| Two-factor      | TOTP (RFC 6238, SHA-1, 6 digits, ±1 step). Up to 10 devices per account; each secret is AES-256-GCM encrypted with associated data bound to the user, and each device has its own atomic replay protection. 10 single-use recovery codes stored as HMACs. Required per role; the last device can't be removed while the role requires it. Only roles below one's own can be changed — except by the owner. |
| Sessions        | 256-bit random tokens; the database stores SHA-256 only. Cookies are `HttpOnly`, `SameSite=Lax`, and `Secure` with the `__Host-` prefix on HTTPS. At most 30 sessions per person. Revoked on password change, reset and role change. The account page addresses sessions by a handle derived from the hash, never by the hash.                                                                             |
| Password reset  | Single-use, 30-minute token, stored as a hash, delivered in the URL fragment (never in server logs or `Referer`). A reset never bypasses 2FA.                                                                                                                                                                                                                                                              |
| Profile changes | Username and e-mail changes need the current password; the old address is notified; pending reset links are invalidated.                                                                                                                                                                                                                                                                                   |

### Requests and content

| Area         | Implementation                                                                                                                                                                                                                                                                                                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CSRF         | Every non-GET API request must carry an `Origin` that matches the configured base URL; the `Host` header is checked against an allow-list (DNS-rebinding protection).                                                                                                                                                                                                               |
| Read access  | Every page declares what it needs and is turned away before anything is loaded. Page titles for the browser tab are only looked up for someone who may read the page, so a private wiki's redirect to the sign-in carries no title (tested for page, history and editor addresses). The language cookie only accepts `de` or `en`.                                                  |
| Markdown     | `html: false` in markdown-it, then an allow-list sanitizer. Attributes such as `target` and `rel` are rebuilt, never copied from input. External links get `target="_blank"` plus `rel="noopener noreferrer nofollow ugc"`.                                                                                                                                                         |
| CSP          | Nonce-based `script-src` with `strict-dynamic`, no `unsafe-inline` scripts, `frame-ancestors 'none'`, frames limited to youtube-nocookie.com and player.vimeo.com, autoplay disabled by Permissions-Policy.                                                                                                                                                                         |
| Database     | Every query is a `sql` tagged template: values always become bound parameters (`$1`, `$2` …), never SQL text. Identifiers come only from fixed allow-lists. A unit test fails on any raw `.query()` outside the database layer. Each transaction is `SERIALIZABLE` with automatic retry; statements time out after 30 s. Database errors reach the client only as generic messages. |
| Search       | Query terms are data: escaped `LIKE` patterns over a trigram index. Wildcards are matched with a linear scan, never a regular expression built from input. Each search has a time budget, all searches together a CPU budget.                                                                                                                                                       |
| Uploads      | Type decided by magic bytes, SVG/HTML refused, image metadata stripped, files served from `/media` with `Content-Security-Policy: sandbox` and `nosniff`, concurrency and quota limits.                                                                                                                                                                                             |
| Import       | Archive paths are only names (no zip-slip); sizes are checked while inflating (zip bombs stop at the limit); everything runs in one transaction.                                                                                                                                                                                                                                    |
| Mail         | Settings-configured servers are limited to mail ports and may not resolve to link-local, metadata or unspecified addresses. DNS is resolved once and the connection pinned to that address. Header values can't contain line breaks. HTML mails escape every value and only link `http(s)`. The test mail only goes to the requesting administrator.                                |
| Live updates | Connections are capped globally and per IP.                                                                                                                                                                                                                                                                                                                                         |

### Private pages and shared links

- **Levels.** A page is readable by everyone who may read the wiki, by administrators and the owner, or by the owner alone. What counts is the page's _effective_ level — the highest of its own and all of its ancestors' — so a section is private as a whole and no sub-page can be more open than its chapter. A page beyond the reader's level is treated as non-existent everywhere: page and editor addresses, history, Markdown and PDF downloads, search, menu, lists, "linked from", previous/next, recent changes, the trash, live updates (which carry no titles and are filtered per connection), exports, imports (a hidden page with a colliding address is never overwritten — the import gets a new address), the backup page list and single-page restore, and the media library. Every such answer is the same "not found" as for an address that was never used. Only the owner may set or remove "owner only".
- **No accidental exposure.** New pages under a private chapter are private at once. Moving a page raises its own level to what it had, so it never becomes more visible by moving — opening it up again is an explicit visibility change (logged). Deleting a private chapter raises its direct sub-pages so they stay private once they move up; the trash keeps each page's level. Front matter can make an imported page private, never more private than the importer may see.
- **Shared links** are 256-bit random tokens (base64url, 43 characters). The database keeps the SHA-256 and a four-character hint only; the link is shown once. A link resolves only if it hasn't expired, its page still exists, its creator is still an active administrator or the owner, and the page's effective level is within the creator's level — all checked on every request, so a demotion, disablement, deletion or tightened visibility ends the link at once. A section link includes only sub-pages whose level doesn't exceed the shared page's. All failures (malformed, unknown, expired, revoked, out of scope) answer the same 404; look-ups are rate-limited per address. The shared view renders only pages in its scope, rewrites in-scope links and media to go through the token, never shows authors, menu, search or the rest of the wiki, and is `noindex` (header and meta). `Referrer-Policy: no-referrer` keeps the token out of other sites' logs. Media through a link (`/s/media/<token>/<file>`) is served only for files that a page in the link's scope references. The link's PDF shows the wiki's base address, never the token. Only administrators and the owner create links; administrators see and revoke only links to pages within their level. At most 20 working links per page and 1000 overall. Links aren't in backups; a full restore drops them.
- **PDF export** builds the document from the page's Markdown tokens, never from HTML. Layout runs in a worker thread (45 s, 512 MB heap, at most two at a time — more answer 503) so a hostile page can't block the server; finished PDFs are cached by content. Only the wiki's own PNG/JPEG files are read from disk (name pattern checked, at most 50 megapixels each, 60 images and 60 MB per PDF) and their metadata stripped; everything else — external images, other formats, videos, embeds — becomes a link. pdfmake's access policies in the worker refuse every URL and allow file reads only of the bundled fonts; images are handed over as bytes the wiki read and checked itself. Link targets are limited to `http(s)`, `mailto` and the wiki's own addresses. Downloads are `Content-Disposition: attachment`, `no-store`, and carry `Content-Security-Policy: default-src 'none'; sandbox`.

**Known limits.** The security log (administrators only) names pages, including private ones it records actions on. Media files are capability URLs: a file that only private pages show is refused to everyone below their level in the library and at `/media`, but once someone knows its random name it can't be "un-known" — use a new upload for something that must stay private after a name leaked. Creating a page at an address that a private page already uses fails, which tells an editor that some page uses that address (not its title or content). Owner-only pages are part of the encrypted backups, which only the owner can download.

### Data at rest

- The master key is generated with mode `0600` in the data volume unless `WIKI_MASTER_KEY` / `WIKI_MASTER_KEY_FILE` is set. Keep a copy outside the volume; without it, nobody can sign in and all 2FA has to be reset.
- PostgreSQL runs in its own container on an internal Docker network with no published port. The wiki connects as a dedicated user that owns only its database: no superuser, no `CREATEDB`/`CREATEROLE`, so `COPY … TO PROGRAM`, `pg_read_file` and friends fail (tested). The superuser password is only given to the database container.
- After an erasure, a final deletion or a deleted upload the affected tables are rewritten with `VACUUM FULL` (plain `VACUUM` leaves the bytes in the file — tested against the raw files). It waits at most 2 s for the table and otherwise retries from a persistent list. Self-erased accounts leave a tombstone (id and time only) so no backup can bring them back.
- **Backups** are encrypted and authenticated before they leave the wiki: per-file keys derived with HKDF from the master key and a random salt, AES-256-GCM in 64 KiB chunks with a counter-and-last-chunk nonce (reordering, truncation, swapping files between backups all fail), media stored under HMAC names. Settings for the backup target and the S3 secret are never part of a backup. Uploaded backups are decrypted and checked completely before they are accepted.
- **Backup folders** chosen in the settings must lie inside an allow-list of roots (`WIKI_BACKUP_ROOTS`), exist already, and contain no symbolic link; system folders and the wiki's own data are refused. Inside a backup folder the wiki never follows a link (`O_NOFOLLOW`, every path step checked), so whoever can write to a NAS share can't make it read, overwrite or delete files elsewhere. Changing the storage needs the owner's password, which is checked before the folder is.
- **Appearance** values are checked one by one before they're stored or rendered (hex colours, known ids, whole numbers in range, a background image that must be `/media/<name>` of this wiki); anything else refuses the whole change. The generated stylesheet can't close its `<style>` element. Fonts are served by the wiki itself.
- **Custom CSS** is owner-only and needs the password. It may not load anything from elsewhere: no `@import`, and `url()`/`image-set()` only to paths of this wiki or inline images — CSS escapes and comments are decoded first — so attribute selectors can't send what someone types to another server.
- **S3 targets** are signed with SigV4 (tested against AWS's reference signer). The endpoint is resolved once and the connection pinned to that address; link-local, metadata, unspecified and multicast addresses are refused. Errors from the storage are logged on the server, never relayed to the browser. Only the owner sees or changes the S3 details, with their password.
- The container starts as root only to apply `PUID`/`PGID` to `/data`, then drops privileges. Application files are read-only for the runtime user.

### Testing

The test suites cover these properties directly: XSS corpus against the renderer, CSRF and DNS-rebinding requests, privilege escalation attempts, replay of TOTP codes and recovery codes, IDOR on sessions and devices, a fuzzer that sends malformed bodies to every endpoint, login and connection floods, hostile search queries and archives, an upgrade from the previous database schema and from SQLite, SQL-injection payloads against every query path, hostile backup archives, tampered ciphertext, and the backup permission matrix, every page path, list, search, export, import and event against private pages at each level, shared-link guessing, path tricks, expiry, revocation and creator demotion, and PDF export of hostile, huge and image-heavy pages.
